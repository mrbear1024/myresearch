# 三个近期问题的事后分析（Postmortem）

> 来源：https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues
> 发布时间：2024年

在这篇文章中，我们分享了影响 Claude API 的三个近期问题的详细信息，包括其原因、修复方式，以及我们为防止类似问题再次发生所采取的措施。

## 事件1：令牌生成配置错误（8月25日）

8月25日，一项配置错误被部署到 Claude API 的 TPU 服务器上，导致令牌生成（token generation）过程中出现错误。一项运行时性能优化偶尔会将高概率赋予那些本应极少产生的令牌。

### 影响
用户遭遇了输出质量下降的问题，包括意外字符、乱码文本和无意义的回复。该问题具有间歇性，通过标准监控手段难以检测。

### 根本原因
令牌生成流水线（token generation pipeline）中的一项性能优化引入了一个微妙的缺陷（bug），导致概率分布发生偏移。在特定条件下，低概率令牌获得了不成比例的高采样权重。

### 解决方案
我们回滚了该优化，并在部署流程中添加了针对意外字符输出的检测测试。

## 事件2：输出质量下降

另一个独立的问题导致用户反馈 Claude 的输出感觉"不一样"或质量下降。这种变化足够微妙，以至于自动化基准测试没有将其标记出来，但用户注意到了语气、有用性和推理质量方面的差异。

### 根本原因
服务基础设施（serving infrastructure）的变更无意中影响了模型行为。我们的验证流程通常依赖基准测试以及安全评估和性能指标，由工程团队进行抽样检查，并先部署到小规模的"金丝雀"（canary）测试组。

然而，这些问题暴露了关键的缺口——我们运行的评估未能捕捉到用户所报告的质量下降。

### 经验教训
- 自动化基准测试并不总能捕捉到现实世界中的质量变化
- 用户反馈是一个关键信号，应被系统性地纳入
- 金丝雀部署（canary deployments）需要运行更长时间，并覆盖更多样化的工作负载

## 事件3：错误率升高

第三个事件导致部分 API 用户的错误率升高，造成请求失败和可靠性下降。

### 根本原因
基础设施扩缩容（scaling）变更未考虑到流量分布模式，导致某些服务器组在高峰使用期间过载。

### 解决方案
我们重新平衡了流量分布，并改进了容量规划以应对这些流量模式。

## 我们正在采取的措施

针对这些事件，我们正在进行以下改进：

### 更快速的调试工具
我们正在开发基础设施和工具，以便在不牺牲用户隐私的前提下更好地调试来自社区的反馈。在这些事件处理过程中开发的一些定制工具将被用于缩短未来事件的修复时间。

### 改进评估覆盖范围
我们已扩展了评估套件，纳入了更细致的质量指标，以更好地匹配用户感知的质量。这包括：
- 对话质量评估
- 长文本输出评估
- 与基线模型的并排对比

### 增强部署安全措施
- 针对意外字符输出的检测测试
- 更长的金丝雀部署周期
- 发布期间更多样化的评估工作负载
- 针对细微质量变化的改进监控

### 社区反馈整合
我们正在构建更好的系统，将用户反馈纳入我们的部署验证流程，确保真实世界的质量信号能够补充自动化基准测试。

## 结论

这些事件强化了一个认识：可靠地提供大语言模型（large language models）服务不仅需要模型质量，还需要稳健的基础设施、全面的评估以及对用户反馈的密切关注。我们致力于在这三个方面持续改进。
