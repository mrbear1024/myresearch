# 我们如何构建多代理研究系统

> 来源: https://www.anthropic.com/engineering/multi-agent-research-system
> 发布日期: 2025年

Research功能使用多个Claude代理来更有效地探索复杂主题。在这篇文章中，我们分享了构建该系统过程中遇到的工程挑战和经验教训。

以Claude Opus 4作为主导代理、Claude Sonnet 4子代理（subagents）组成的多代理系统，在我们的内部研究评估中比单代理Claude Opus 4的表现提升了90.2%。

## 为什么选择多代理？

有些研究任务对于在单个上下文窗口（context window）中运行的单个代理来说过于复杂。它们需要同时探索多个来源，从不同角度综合信息，并管理超出单个窗口容量的上下文。

我们发现多代理系统在以下类型的任务中表现出色：
- 跨多个来源的大规模并行化
- 超出单个上下文窗口容量的信息
- 与众多复杂工具的交互

## 架构

Research系统采用了**协调者-工作者模式（orchestrator-worker pattern）**的多代理架构。一个主导代理（Claude Opus 4）分解研究问题，将子任务委派给工作者代理（Claude Sonnet 4），并综合它们的发现。

### 扩展规则（Scaling Rules）

代理很难判断不同任务所需的适当工作量，因此我们在提示中嵌入了扩展规则：
- **简单事实查找**：1个代理，3-10次工具调用
- **中等研究**：3-5个子代理，各有专注的职责
- **复杂研究**：超过10个子代理，职责明确划分

## 提示策略（Prompting Strategy）

我们的提示策略注重灌输良好的启发式方法（heuristics），而非僵化的规则。我们研究了熟练的人类如何处理研究任务，并将这些策略编码到我们的提示中。

### 引导思维过程

我们不是规定确切的步骤，而是引导代理的推理过程——鼓励它考虑多种假设，寻找反面证据，并跨来源进行综合。

### 教协调者如何委派

主导代理需要知道何时委派任务、何时自己处理子任务。我们发现，在提示中明确委派标准可以显著改善任务分配。

### 并行工具调用（Parallel Tool Calling）

子代理可以并行执行多个工具调用，大幅减少总研究时间。协调者协调这些并行工作并管理信息流。

## Token使用模式

根据我们的数据：
- 代理通常使用的token量约为聊天交互的**4倍**
- 多代理系统使用的token量约为聊天的**15倍**

这使得token效率对多代理系统至关重要。我们使用积极的压缩（compaction）和选择性信息传递来控制成本。

## 经验教训

1. **从简单开始，仅在需要时增加复杂度**：不是每个研究问题都需要10个子代理。系统应该根据查询复杂度来调整工作量。
2. **子代理的质量比数量更重要**：少数几个提示良好的子代理胜过许多指导不当的子代理。
3. **信息综合是最难的部分**：将多个代理的发现组合成连贯、不冗余的回复需要精心的协调。
4. **评估至关重要**：我们构建了自定义评估来衡量研究质量，包括事实准确性、完整性和来源多样性。

## 结果

在我们的内部研究基准测试中，多代理系统显示出显著的改进：
- 比单代理Claude Opus 4提升了90.2%
- 更好的来源多样性和事实覆盖率
- 更结构化和全面的输出

从原型到生产的过程教会了我们关于系统架构、工具设计和提示工程（prompt engineering）的关键经验，这些经验远远超出了研究任务本身的适用范围。
