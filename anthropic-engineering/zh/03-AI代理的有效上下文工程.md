# AI 代理的有效上下文工程

> 来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
> 作者：Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield
> 发布日期：2025年9月29日

随着我们朝着构建更强大的代理迈进——这些代理在多轮推理和更长的时间跨度上运行——我们需要管理整个上下文状态的策略：系统指令、工具、模型上下文协议（MCP）、外部数据、消息历史等等。

提示工程（Prompt Engineering）关注的是找到正确的词语。上下文工程（Context Engineering）关注的是找到正确的系统配置。在这篇文章中，我们分享了从构建 Claude Code 和其他代理系统中学到的经验——关于精心策划有限上下文窗口内容的艺术与科学。

## 从提示工程到上下文工程

提示工程问的是："我该如何措辞这个指令？"上下文工程问的是："什么样的上下文总体配置最有可能从我的模型中产生我想要的行为？"

上下文——在从 LLM 采样时包含的 token 集合——已经远远超出了单个提示的范畴。它现在涵盖系统提示、工具定义、MCP 集成、外部数据源和不断演变的消息历史。鉴于 LLM 受到有限注意力预算的约束，好的上下文工程意味着找到最小的高信号 token 集合，以最大化某个期望结果的可能性。

| 提示工程（Prompt Engineering） | 上下文工程（Context Engineering） |
|---|---|
| 专注于编写和组织指令 | 管理完整的 token 集合 |
| 用于离散任务（分类、生成） | 用于持续的代理操作 |
| 重点在系统提示 | 包括工具、MCP、外部数据、历史 |
| 离散任务 | 迭代和持续 |

## 注意力预算

LLM 在基本架构约束下运行。就像人类的工作记忆一样，它们的有效注意力是有限的。随着我们向上下文中添加更多 token，模型精确检索和使用特定信息的能力可能会下降——我们称这种现象为**上下文退化（context rot）**。

这不是任何特定模型的缺陷——这是所有模型中都会出现的特征。实际含义是，我们需要对进入上下文窗口的内容保持有意识的选择。

## 系统提示结构

将提示组织成不同的部分——使用 XML 标签或 Markdown 标题等技术来划分这些部分——有助于 Claude 有效地导航它们。我们建议使用 `<background_information>`、`<instructions>`、`## Tool guidance` 和 `## Output description` 等结构。

### 黄金区域（Golden Zone）

在提示的具体性和灵活性之间存在平衡。过于刚性，代理无法适应新情况。过于模糊，代理会做出糟糕的决策。"黄金区域"是指令足够具体以指导行为，同时又足够灵活以处理变化的最佳平衡点。

## 少样本示例（Few-shot Examples）

策划一组多样化的、规范的示例，有效展示代理的预期行为，而不是将边缘情况塞入提示中。示例应该展示预期行为的范围，而不仅仅是边缘情况。

## 动态上下文检索

与其预先加载所有可能的上下文，有效的代理会在运行时即时发现和检索上下文。Claude Code 采用混合模型：CLAUDE.md 文件在开始时直接加载到上下文中，而 `glob` 和 `grep` 等原语允许它导航环境并即时检索文件。

### 渐进式披露（Progressive Disclosure）

渐进式披露是代理通过文件大小、时间戳和层次结构等信号逐步发现相关上下文的过程。代理不是一次性倾倒所有信息，而是可以根据需要探索和加载信息——就像开发者导航一个不熟悉的代码库一样。

## 工具设计作为上下文工程

工具被加载到模型的上下文窗口中，这意味着它们的定义会消耗注意力预算。糟糕的工具设计可能会在模糊或重叠的功能上浪费上下文。

关键原则：
- 消除产生歧义的重叠工具
- 保持工具描述简洁但完整
- 使用能清楚传达其用途的工具名称
- 考虑工具定义的总 token 成本

## 压缩（Compaction）

压缩——在接近上下文窗口限制时总结对话内容——是上下文工程中驱动更好长期连贯性的第一个杠杆。在 Claude Code 中，上下文压缩通过将消息历史传递给模型来总结和压缩最关键的细节来实现，保留架构决策、未解决的 bug 和实现细节，同时丢弃冗余的工具输出。

## 结构化笔记（Structured Note-Taking）

代理可以在上下文窗口之外的持久化内存中写入笔记。这些笔记充当外部记忆，代理可以稍后检索，使其能够跨压缩边界维护重要信息。

## 多代理上下文管理

子代理架构提供了另一种强大的上下文管理策略。主代理进行协调，而专门的子代理执行深度技术工作，每个子代理在自己的上下文窗口中操作。子代理向协调器返回压缩的摘要，保持主上下文窗口的整洁。

根据我们的数据，代理通常使用大约 **4 倍于聊天交互**的 token，而多代理系统使用大约 **15 倍于聊天**的 token——这使得上下文效率特别重要。

## 结论

上下文工程代表了提示工程的自然演进。随着代理承担更长期、更复杂的任务，深思熟虑地管理完整的上下文状态——而不仅仅是提示——对于构建可靠、有效的 AI 系统至关重要。
