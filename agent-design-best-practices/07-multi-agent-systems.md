# 7. 多智能体系统（Multi-Agent Systems）

> 学习目标：理解多智能体系统的优势与架构模式，掌握子智能体设计的四要素，了解 Token 成本与扩展策略。
>
> 来源：Anthropic Engineering Blog, "How We Built Our Multi-Agent Research System"

## 7.1 为什么需要多智能体

Alex Albert（Anthropic）指出：多智能体系统在复杂任务上的表现比单智能体**提升 90%+**。

```
演进路径（类比软件架构）：

单体应用          →        微服务架构
  │                           │
  ▼                           ▼
单智能体          →        多智能体系统
(一个模型做所有事)           (专门化的智能体协作)
```

**何时使用单智能体 vs 多智能体**：

| 场景 | 推荐方案 |
|------|---------|
| 简单的问答和对话 | 单智能体 |
| 单一领域的工具操作 | 单智能体 |
| 需要多领域专业知识 | 多智能体 |
| 复杂的研究任务 | 多智能体 |
| 需要并行处理的任务 | 多智能体 |
| 长时间运行的工作流 | 多智能体 |

## 7.2 架构模式

### Lead Agent + SubAgents 模式

最常见的多智能体架构：一个领导智能体负责任务分解和调度，多个子智能体负责具体执行。

```
                  ┌──────────────┐
                  │   用户请求    │
                  └──────┬───────┘
                         ▼
                  ┌──────────────┐
                  │  Lead Agent  │  ← Claude Opus (最强模型)
                  │  任务分解     │
                  │  结果汇总     │
                  └──────┬───────┘
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
   ┌─────────────┐┌─────────────┐┌─────────────┐
   │ SubAgent A  ││ SubAgent B  ││ SubAgent C  │
   │ 研究员      ││ 编码者      ││ 审查者       │  ← Claude Sonnet
   │             ││             ││             │
   │ 工具:       ││ 工具:       ││ 工具:       │
   │ search      ││ edit        ││ read        │
   │ web_fetch   ││ write       ││ search      │
   │ read        ││ bash        ││ comment     │
   └─────────────┘└─────────────┘└─────────────┘
```

### Anthropic 多智能体研究系统实例

Anthropic 在其工程博客中描述了他们构建的多智能体研究系统：

```
用户查询
    │
    ▼
┌─────────────┐
│ Lead Agent  │ ← 分析查询复杂度
│             │ ← 制定研究计划
│             │ ← 分配子任务
└──────┬──────┘
       │
       ├──▶ SubAgent 1: 搜索学术论文
       ├──▶ SubAgent 2: 分析行业报告
       ├──▶ SubAgent 3: 收集案例数据
       │
       ◀── 汇总所有子智能体结果
       │
       ▼
┌─────────────┐
│ Lead Agent  │ ← 综合分析
│ 最终报告     │ ← 交叉验证
└─────────────┘
```

## 7.3 子智能体设计四要素

每个子智能体都需要明确定义以下四个维度：

### 要素一：明确目标（Clear Objective）

```
❌ 模糊目标：
  "研究一下这个主题"

✅ 明确目标：
  "搜索最近 6 个月内关于 'AI agent safety' 的学术论文，
   提取每篇论文的核心观点、方法论和结论，
   输出一个包含 5-10 篇论文摘要的结构化报告。"
```

### 要素二：输出格式（Output Format）

```typescript
// 在系统提示中明确定义输出格式
const subagentPrompt = `
你是一个研究助手。完成任务后，请以下列 JSON 格式输出：

{
  "findings": [
    {
      "source": "来源名称",
      "key_points": ["要点1", "要点2"],
      "relevance_score": 0.0-1.0,
      "summary": "一句话总结"
    }
  ],
  "confidence": "high | medium | low",
  "gaps": ["未能覆盖的方面"]
}
`;
```

### 要素三：工具指导（Tool Guidance）

告诉子智能体**何时使用哪个工具**，而非仅提供工具列表：

```
工具使用指导：
1. 首先使用 web_search 搜索关键词
2. 对搜索结果中相关度高的链接，使用 web_fetch 获取全文
3. 使用 read 读取本地已有的相关文件
4. 不要使用 edit 或 write — 你是研究智能体，不做修改
```

### 要素四：边界定义（Defined Boundaries）

```
边界约束：
- 时间范围：只关注 2024 年之后的资料
- 领域范围：只关注 AI 安全，不涉及通用 AI 能力研究
- 深度范围：每个来源最多分析 3 个关键点
- 数量范围：最多处理 10 个搜索结果
- 禁止操作：不得修改任何文件，不得执行代码
```

## 7.4 Token 成本与扩展策略

**成本对比**：

| 交互方式 | 相对 Token 用量 | 适用场景 |
|----------|----------------|---------|
| 单次聊天 | 1x (基准) | 简单问答 |
| 单智能体 | 4x | 工具密集任务 |
| 多智能体 | 15x | 复杂研究任务 |

**成本控制策略**：

### 策略一：在提示中嵌入扩展规则

```
根据查询复杂度调整工作量：
- 简单事实查询 → 最多 2 次搜索，直接回答
- 中等分析任务 → 3-5 个子任务，使用 2 个子智能体
- 复杂研究任务 → 5-10 个子任务，使用 3-5 个子智能体
```

### 策略二：模型分层

```
协调者 (Orchestrator): Claude Opus    ← 最强推理能力
执行者 (Workers):      Claude Sonnet  ← 高性价比
分类器 (Classifier):   Claude Haiku   ← 最低成本
```

### 策略三：提前终止

```typescript
// 当子智能体发现信息足够时提前终止
const EARLY_STOP_CONDITIONS = {
  maxToolCalls: 20,         // 最多 20 次工具调用
  maxTokens: 50000,         // 最多 50K token
  confidenceThreshold: 0.9, // 信心度达到 0.9 即停止
};
```

### 策略四：结果缓存

```
子智能体 A 搜索结果 ──▶ 缓存层 ──▶ 子智能体 B 可复用
                           │
                     避免重复搜索
```

## 7.5 多智能体通信模式

### 串行通信

```
Agent A ──结果──▶ Agent B ──结果──▶ Agent C
```

适用：流水线任务，后一步依赖前一步的结果。

### 并行通信

```
          ┌──▶ Agent A ──┐
Lead ─────├──▶ Agent B ──┼──▶ Lead（汇总）
          └──▶ Agent C ──┘
```

适用：独立子任务可同时执行。

### 迭代通信

```
Agent A ◀──反馈──▶ Agent B
   │                 │
   └──多轮交互────────┘
```

适用：需要协商或迭代改进的任务（如代码审查）。
