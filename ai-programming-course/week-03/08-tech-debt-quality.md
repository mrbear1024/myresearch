# 07 — 技术债务与质量

> 学习目标：理解技术债务的概念，学会在速度和质量之间做平衡。

## 什么是技术债务

技术债务（Tech Debt）就像金融债务一样：为了短期速度而走的捷径，将来需要花更多时间来偿还。

```
快速但粗糙的实现 → 当下节省 2 天 → 未来多花 2 周维护
```

### 技术债的例子

| 捷径 | 短期收益 | 长期代价 |
|------|---------|---------|
| 不写测试 | 开发快 30% | 每次改动都可能引入 bug |
| 硬编码配置 | 快速跑通 | 每次部署都要改代码 |
| 复制粘贴代码 | 马上能用 | 改一个地方要改 N 处 |
| 不写文档 | 省 1 小时 | 新人入职花 1 周搞懂 |
| 忽略错误处理 | 代码更简短 | 线上报错排查困难 |

## 技术债不全是坏的

有些技术债是**刻意的、合理的**：

```
✅ 合理的技术债：
"MVP 阶段先不做国际化，验证市场后再加" — 有意识的取舍

❌ 不合理的技术债：
"太赶了，随便写写先" — 无意识的偷懒
```

关键区别：你是否**知道**自己在欠债，以及是否有**偿还计划**。

## 如何识别技术债

### 信号

- 改一个小功能需要花很长时间
- 修一个 bug 会冒出新的 bug
- 新成员入职需要很长时间才能上手
- 大家害怕碰某些文件或模块
- 「先别动那个文件」成为团队口头禅

### 度量

```bash
# 代码复杂度：看哪些文件最复杂
# 变更频率：看哪些文件改得最多
# Bug 热点：看 bug 总是出在哪些模块

git log --format=format: --name-only | sort | uniq -c | sort -rn | head -20
```

上面的命令会列出修改最频繁的文件——它们往往是技术债集中的地方。

## 偿还策略

### 1. 童子军规则

> 离开营地时，让它比你来时更干净。

每次改动一个文件时，顺手做一点小改善（改善命名、提取函数、添加注释），但不要大改。

### 2. 20% 法则

每个迭代拿出 20% 的时间专门偿还技术债，而不是 100% 做新功能。

```
每周 5 天开发时间：
- 4 天做新功能
- 1 天偿还技术债（重构、补测试、写文档）
```

### 3. 技术债登记

维护一个技术债清单，记录：

```markdown
## 技术债清单

### 高优先级
- [ ] chat.ts 需要拆分（400 行，涉及 3 种职责）
- [ ] API 缺少错误处理和重试逻辑

### 中优先级
- [ ] 组件缺少 TypeScript 类型
- [ ] 没有自动化测试

### 低优先级
- [ ] CSS 类名不统一
- [ ] 部分注释已过时
```

## 质量的维度

| 维度 | 衡量标准 | 工具 |
|------|---------|------|
| 正确性 | 功能是否符合预期 | 测试 |
| 可读性 | 代码是否容易理解 | Code Review |
| 可维护性 | 修改是否容易 | 模块化程度 |
| 性能 | 响应速度是否够快 | Lighthouse |
| 安全性 | 是否有漏洞 | 安全扫描 |

## 速度 vs 质量

这不是非此即彼的选择，而是一个**滑动的刻度**：

```
全速度（无质量）  ←──────→  全质量（无速度）
        ↑                       ↑
     黑客马拉松              航天软件

大多数项目应该在这里 → [====|=====]
                        速度  质量
```

- **探索阶段**（不确定做什么）：偏速度
- **增长阶段**（产品已验证）：逐步提高质量
- **成熟阶段**（大量用户依赖）：偏质量

## 关键收获

1. **技术债是决策**：有意识地欠债，有计划地偿还
2. **童子军规则**：每次改动都让代码变好一点
3. **20% 法则**：持续投入时间偿还技术债
4. **阶段匹配**：不同阶段对质量的要求不同
5. **不要追求完美**：追求「足够好」而不是「完美」
