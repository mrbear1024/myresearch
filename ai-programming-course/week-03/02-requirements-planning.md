# 02 — 需求与规划

> 学习目标：学会用 MVP 思维分析需求，制定合理的迭代计划，避免过度设计。

## 最大的浪费：做了不该做的功能

软件项目失败的首要原因不是代码写得不好，而是**做了错误的东西**。

研究表明，软件产品中 65% 的功能很少或从不被使用。这意味着大部分开发时间被浪费在了用户不需要的东西上。

## MVP 思维

### 什么是 MVP

MVP（Minimum Viable Product，最小可行产品）= 用最少的功能验证最核心的假设。

```
❌ 错误思路：先把所有功能都做好，然后一次性发布
✅ 正确思路：先做最核心的一个功能，发布，获取反馈，再决定下一步
```

### 案例：做一个笔记应用

```
❌ 完美主义的计划：
1. 支持 Markdown 编辑
2. 文件夹分类
3. 标签系统
4. 全文搜索
5. 多端同步
6. 协作编辑
7. AI 写作助手
8. 导出为 PDF/Word
→ 预计开发 6 个月 → 6 个月后发现没人用

✅ MVP 的计划：
1. 创建和编辑纯文本笔记
2. 笔记列表
→ 预计开发 1 周 → 给 10 个朋友试用 → 根据反馈决定下一步
```

### MVP 不是做烂产品

MVP 是「小而精」，不是「小而烂」：

- 功能少，但每个功能都好用
- 界面简单，但不丑
- 场景少，但核心场景流畅

## 用户故事

用户故事是描述需求的一种简洁格式：

```
作为 [角色]，我想要 [功能]，以便 [价值]
```

### 例子

```
作为一个用户，我想要用邮箱注册账号，以便保存我的聊天记录。
作为一个用户，我想要发送消息给 AI，以便获得编程帮助。
作为一个用户，我想要查看历史对话，以便回顾之前的解决方案。
```

### 优先级排序

用 **MoSCoW 方法** 给用户故事排优先级：

| 级别 | 含义 | 例子 |
|------|------|------|
| **Must have** | 没有就不能用 | 发送消息、接收 AI 回复 |
| **Should have** | 重要但不紧急 | 保存对话历史 |
| **Could have** | 锦上添花 | 深色模式 |
| **Won't have** | 本次不做 | 多人协作、语音输入 |

先做完所有 Must have，再考虑 Should have。

## 迭代规划

### 时间盒（Timeboxing）

给每个迭代设定固定的时间（通常 1-2 周），时间到了就发布，而不是功能做完了才发布。

```
迭代 1（第 1 周）：用户注册 + 发送消息 + AI 回复
迭代 2（第 2 周）：对话历史 + 消息持久化
迭代 3（第 3 周）：UI 优化 + 错误处理
```

### 每个迭代的结构

```
计划（2 小时）→ 开发（4 天）→ 测试（半天）→ 发布（半天）→ 回顾（1 小时）
```

## 用 AI 辅助需求分析

AI 在需求阶段也能帮忙：

```
提示词示例：

我想做一个 [产品描述]。目标用户是 [用户描述]。
请帮我：
1. 列出核心功能（Must have）
2. 列出次要功能（Should have）
3. 建议 MVP 的范围
4. 给出 3 个迭代的开发计划
```

## 需求文档模板

一个简单实用的需求文档：

```markdown
# 项目名称

## 一句话描述
[用一句话说清楚这个项目是什么]

## 目标用户
[谁会用这个产品]

## 核心问题
[解决用户的什么痛点]

## MVP 功能列表
- [ ] 功能 1（Must have）
- [ ] 功能 2（Must have）
- [ ] 功能 3（Should have）

## 迭代计划
### 迭代 1：[主题]（[时间]）
- [ ] 任务 1
- [ ] 任务 2

## 技术方案
- 前端：Next.js + TypeScript
- 后端：Supabase
- 部署：Vercel
```

## 关键收获

1. **先验证再开发**：用 MVP 快速验证想法，避免做没人要的功能
2. **用户故事**：用「作为...我想要...以便...」格式描述需求
3. **MoSCoW 排序**：分清 Must / Should / Could / Won't
4. **时间盒迭代**：固定时间发布，而不是等功能做完
5. **AI 辅助**：让 AI 帮你做需求分析和计划拆解
