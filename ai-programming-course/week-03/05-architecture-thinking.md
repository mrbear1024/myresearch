# 04 — 架构思维

> 学习目标：理解常见的软件架构模式，学会在技术选型中做出合理的取舍。

## 什么是架构

架构是关于「大的组织方式」的决策：

- 系统分成几个部分？
- 各部分之间怎么通信？
- 数据在哪里存储和流动？
- 哪些决策现在必须做，哪些可以以后再说？

架构决策通常很难改变（改变成本高），所以值得在动手前多想一步。

## 前后端分离 vs 全栈一体

### 全栈一体（Monolith）

```
Next.js 应用
├── 前端页面（React）
├── API 路由（Server Actions / Route Handlers）
└── 数据库访问（Supabase Client）
```

- **适合**：个人项目、小团队、MVP
- **优点**：简单、部署方便、开发速度快
- **缺点**：前后端耦合，难以独立扩展

### 前后端分离

```
前端（Next.js）  ←→  后端 API（Express / FastAPI）  ←→  数据库
```

- **适合**：需要多个客户端（Web + App）、团队分工
- **优点**：前后端独立开发和部署、可以用不同技术栈
- **缺点**：复杂度更高、需要处理 CORS 等问题

### 本课程的选择

我们使用 **Next.js 全栈一体** 方案。对于个人项目和 MVP，这是最高效的选择。

## 单体 vs 微服务

| 特性 | 单体（Monolith） | 微服务（Microservices） |
|------|-----------------|----------------------|
| 部署 | 一个应用 | 多个独立服务 |
| 复杂度 | 低 | 高 |
| 团队规模 | 1-10 人 | 10+ 人 |
| 适合阶段 | 早期、验证阶段 | 成熟、需要独立扩展 |
| 调试 | 简单 | 分布式追踪 |

> 💡 **先做单体，有了明确的拆分理由后再考虑微服务。** 过早微服务化是最常见的过度工程。

## 技术选型的思考框架

选择技术时，考虑这几个维度：

### 1. 团队能力

```
❌ 选最热门的技术
✅ 选团队最熟悉的技术
```

### 2. 社区生态

- 文档是否完善？
- 遇到问题能否搜到解决方案？
- 有多少人在生产环境使用？

### 3. 长期维护

- 项目是否活跃维护？
- 背后有没有公司或社区支撑？
- 升级路径是否清晰？

### 4. 匹配场景

不同场景有不同的最佳选择：

| 场景 | 推荐方案 |
|------|---------|
| 个人项目 / MVP | Next.js + Supabase + Vercel |
| 内容网站 / 博客 | Astro / Hugo |
| 移动应用 | React Native / Flutter |
| 高并发 API | Go / Rust |
| 数据处理 | Python |

## 做决策的原则

1. **YAGNI（You Ain't Gonna Need It）**：不要为假想的未来需求做设计
2. **先让它工作，再让它好看，最后让它快**
3. **选择无聊的技术**：成熟稳定的技术比新潮的技术更可靠
4. **可逆 vs 不可逆决策**：可逆的决策快速做，不可逆的决策慎重做

## 关键收获

1. **先单体后微服务**：不要过早拆分
2. **全栈一体适合 MVP**：Next.js 是个人项目的最优解
3. **选熟悉的技术**：团队能力 > 技术潮流
4. **YAGNI**：不为假想的需求做设计
5. **架构是权衡**：没有最好的架构，只有最适合当前阶段的架构
