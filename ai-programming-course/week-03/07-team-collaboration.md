# 06 — 团队协作工程

> 学习目标：掌握 Git 协作流程、Code Review 规范和文档文化，学会在团队中高效协作。

## 一个人写代码 vs 一群人写代码

一个人写代码时，你可以随意命名、随时重构、把所有逻辑放在一个文件里。但当多人协作时，这些都会变成灾难。

团队协作的本质是**减少摩擦**：让每个人能独立工作，在合并时不产生冲突。

## Git 协作流程

### GitHub Flow（推荐小团队使用）

```
main ────────────────────────────────────────→
  │                                    ↑
  └── feature/add-chat ───── PR ───── merge
```

步骤：
1. 从 `main` 创建功能分支
2. 在分支上开发和提交
3. 开 Pull Request（PR）
4. 团队 Code Review
5. Review 通过后合并回 `main`
6. 删除功能分支

```bash
# 1. 创建功能分支
git checkout -b feature/add-chat

# 2. 开发、提交
git add .
git commit -m "feat: 添加聊天功能"

# 3. 推送到远程
git push -u origin feature/add-chat

# 4. 在 GitHub 上创建 PR（或用 CLI）
gh pr create --title "添加聊天功能" --body "实现了基础的聊天界面和 API"
```

### 分支命名约定

```
feature/xxx    — 新功能
fix/xxx        — 修复 bug
refactor/xxx   — 重构
docs/xxx       — 文档更新
```

### Commit 信息规范

```
feat: 添加用户注册功能
fix: 修复消息发送失败的问题
refactor: 重构聊天组件
docs: 更新 README
chore: 升级依赖版本
```

格式：`类型: 简短描述`

## Code Review

### 为什么要 Code Review

- **发现 bug**：第二双眼睛能看到你忽略的问题
- **知识共享**：团队成员了解彼此的代码
- **代码质量**：保持代码风格和架构的一致性
- **学习机会**：从他人的代码中学到新的写法

### 给别人 Review 的要点

```
✅ 好的 Review 评论：
"这里用 useMemo 可以避免每次渲染都重新计算"
"这个 API 调用没有错误处理，如果服务器返回 500 会怎样？"
"建议把这个逻辑提取为 useChat hook，其他页面也能复用"

❌ 坏的 Review 评论：
"这代码写得不好"（不具体）
"我不喜欢这种写法"（没有理由）
"为什么不用 xxx？"（应该说明为什么 xxx 更好）
```

### 接受 Review 的心态

- 代码 Review 是对代码的评价，不是对人的评价
- 每条 Review 意见都是学习机会
- 不同意时，解释你的理由而不是硬扛

## 文档文化

### 必须维护的文档

| 文档 | 用途 | 何时更新 |
|------|------|---------|
| `README.md` | 项目说明和快速开始 | 项目初始化时，重大变更时 |
| `CLAUDE.md` | AI 编程规则 | 添加新规范时 |
| `.env.example` | 环境变量模板 | 添加新环境变量时 |
| PR 描述 | 变更说明 | 每次提 PR 时 |

### 好文档的特征

- **给新人看**：假设读者对项目一无所知
- **可操作**：有具体的命令和步骤，而不只是概念描述
- **保持更新**：过时的文档比没有文档更糟糕

## 关键收获

1. **GitHub Flow**：简单有效的分支协作模型
2. **规范的 Commit**：`feat/fix/refactor: 描述` 格式
3. **Code Review**：具体、建设性、对事不对人
4. **文档先行**：README、CLAUDE.md、.env.example 是必备文档
5. **减少摩擦**：好的流程和规范让团队协作更顺畅
